# Dataset processing workspace

FluxPort shares indexed collection services across the browser, REST API and Go CLI. SQLite remains the metadata store and disposable record index. DuckDB is included in the standard build and initialized for analytical queries or Parquet operations when needed. Simple text conversions stay in Go.

## Excel and Parquet

Import `.xlsx` and `.parquet` from Collections. Browse, filter, join and transform their normalized records using the existing explorer and pipelines. Binary sources are read-only. Watcher refreshes use the same atomic index-generation publication as text files.

- Excel accepts exactly one worksheet with non-empty unique headers. Cells import as raw text, including raw numeric date serials. Formula-bearing sheets are rejected rather than using stale cached results. Compressed input uses the configured document ceiling (16 MiB by default); expanded archive size is capped at 64 MiB and 4,096 entries. Empty cells become empty strings.
- Excel exports use text cells to preserve identifiers, long numbers and formula-like strings. Objects and arrays become JSON text. Null and missing values become blank cells. Workbooks have at most 2,048 columns, 1,048,575 data rows, and conservatively 32,767 bytes per cell. Styles, formulas, date formatting and workbook metadata are not preserved.
- Ordinary typed Parquet files import with DuckDB. Date/time values normalize to text. FluxPort Parquet exports use one VARCHAR column named `__fluxport_record_json_v1`, containing exact JSON records, with Zstandard compression. Reimport recognizes that reserved single-column envelope and restores nested values and exact numbers. This is a fidelity-oriented interchange format, **not a typed analytical Parquet export schema**. Ordinary files using that reserved column name must contain valid JSON records.
- Downloads are prepared as cancellable background jobs from the collection page, filtered explorer, or pipeline. Parquet exports use an intermediate NDJSON file on disk, never an in-memory dataset. Temporary files are removed on errors; completed downloads expire after 24 hours.

DuckDB memory, spill-storage limits and timeouts apply to Parquet queries. File paths are generated by trusted server code; user SQL cannot use these file readers. Both staging and output retain the configured free-disk reserve.

DuckDB operations share a concurrency gate: at most two by default, limited by available Go CPUs, or the configured worker count when provided. Foreground SQL and Parquet jobs share that gate. Waiting requests honor their deadlines and cancellation rather than opening another engine instance.

## Profiling and validation

Open a collection and choose **Inspect data quality**. The default scan checks the first 10,000 records in source order; choose up to 100,000. Reports state coverage and whether the scan is partial. They are tied to one immutable index generation.

Column statistics include observed types, missing/null counts, distinct counts capped at 1,024, precise numeric min/max, means rounded to eight decimals, and Unicode string lengths. Numeric statistics exclude numbers over 1,024 digits or exponent magnitude 1,024 and expose `numeric_skipped`; values remain unchanged. At most 256 columns are profiled. Median, frequency distributions and whole-dataset duplicate estimates are not implemented.

Rules are a JSON array:

```json
[
  {"field":"id","required":true,"type":"integer","unique":true},
  {"field":"customer.email","type":"string","non_empty":true,"pattern":"^[^@]+@[^@]+$"},
  {"field":"amount","type":"number","min":0,"max":1000000},
  {"field":"status","enum":["pending","paid","cancelled"]},
  {"field":"date","date_layout":"2006-01-02"}
]
```

Fields accept dotted paths or JSON pointers (including array indexes). Rules support required, non-null, non-empty, type, numeric range, Unicode length, RE2 regex, enum, date layout and uniqueness. `min_length` and `max_length` apply to strings. Up to 64 rules are allowed. Unique checks retain bounded hashes for at most 10,000 distinct values per rule and fail explicitly if that bound is exceeded. Reports retain the first 200 issues and count all failures in the checked records. Source rows are one-based. Validation never silently discards records.

Save rules per collection or include `validation` in a pipeline definition. Pipeline validation checks transformed output and rejects the entire export on the first failing record; no partial download is published. Final previews validate only their first 20 records. Intermediate previews do not check final-output rules. Skip/quarantine policies, SQL validation and schema-drift rules remain future work.

API routes, protected by the existing configured API key:

| Route | Behavior |
|---|---|
| `GET /api/collections/{id}/profile?limit=10000` | Bounded source profile |
| `POST /api/collections/{id}/validate` | Body: `{"limit":10000,"rules":[...]}`; omitted rules use saved rules |
| `GET /api/collections/{id}/validation-rules` | Saved rule array |
| `PUT /api/collections/{id}/validation-rules` | Body: `{"rules":[...]}` |

These checks inspect indexed source records, before legacy endpoint transformations. Data endpoints retain 503 plus Retry-After while indexing.

## Ordered cleanup steps

Pipelines retain filter, projection, rename, mapping, sorting, deduplication, grouping and joins. Additional operations:

```json
{"op":"transform","transform":{"kind":"trim","field":"name"}}
{"op":"transform","transform":{"kind":"multiply","field":"price","value":1.2,"as":"price_with_tax"}}
{"op":"transform","transform":{"kind":"date","field":"date","layout":"02/01/2006","output_layout":"2006-01-02"}}
{"op":"limit","limit":100}
{"op":"append","append":"another-collection-id"}
```

Transformation kinds: `trim`, `lower`, `upper`, `replace`, `regex`, `substring`, `split`, `merge`, `default`, `cast_string`, `cast_number`, `cast_boolean`, `add`, `subtract`, `multiply`, `date`, `flatten`.

Names address literal top-level fields. `as` sets the output column; without it the original column is replaced. Substring `start`/`length` count Unicode characters; omitted or zero length means through the end. Replace/regex use `find` and `replacement`. Split uses `delimiter`; merge uses `fields`, `delimiter` and `as`. Default fills missing, null or empty-string values using `value`. Flatten creates dotted names, preserves arrays and empty objects, and rejects collisions or nesting beyond 32 levels. Casts are strict: leading-zero text such as `0012` does not silently become a number. Arithmetic uses exact rational values and rejects results outside 1,024 digits or 128 decimal places instead of rounding. Cleanup outputs are capped at 1 MiB per record.

Replacement expansion is checked before allocating output. Regex operations allow at most 32 capture groups and 10,000 matches per record; split allows at most 10,000 items.

Native Go record functions execute inside the existing SQLite pipeline query so operations compose in their declared order without loading the dataset. Pipeline analytical execution has not yet been migrated to DuckDB. The SQL Playground separately supports auto/native/DuckDB selection.

The builder supports per-step previews, reordering, add/remove, JSON configuration and up to 50 undo/redo snapshots. Saving creates recipe revisions; the latest 50 are retained. Restore creates another revision. A supplied stale `revision` returns a conflict rather than overwriting a newer saved definition.

## Runs and schedules

Saved recipes show their recent execution history and output downloads. Existing jobs provide progress, cancellation, retry and interrupted-run recovery. Each job stores the recipe snapshot and source index generations.

Enable automatic runs from a saved pipeline. Intervals are 60 seconds to one year. The server checks due schedules every 15 seconds and queues ordinary jobs; a previous queued/running run prevents overlap for that schedule. Changes to the recipe apply on the next dispatch. Missed intervals are coalesced to a single run after restart; the server must be running. Dispatch errors appear alongside the schedule. A crash between a persisted schedule claim and job submission may skip that interval. Manual runs can still overlap scheduled runs, subject to the worker limit.

Authenticated routes:

- `GET /api/pipelines/{id}/revisions`
- `POST /api/pipelines/{id}/restore` with `{"revision":1}`
- `GET /api/pipelines/{id}/runs`
- `GET /api/pipelines/{id}/schedule`
- `PUT /api/pipelines/{id}/schedule` with `{"interval_seconds":3600,"format":"parquet","enabled":true}`

Scheduling currently prepares downloads; it does not replace source collections or publish API changes. Cron expressions, remote-source refresh, webhook notifications and dataset version restoration remain unimplemented.

## CLI

Commands use `FLUXPORT_DATA_DIR` and `FLUXPORT_STATE_DIR` for the same local workspace:

```sh
fluxport import input.xlsx
fluxport inspect COLLECTION_ID --limit 10000
fluxport validate COLLECTION_ID --rules rules.json
fluxport query --collections COLLECTION_ID --engine duckdb --sql 'SELECT COUNT(*) FROM c_COLLECTION_ID'
fluxport pipeline list
fluxport pipeline run PIPELINE_ID --format parquet --output result.parquet
fluxport export COLLECTION_ID --format xlsx --output result.xlsx
```

Import returns a collection ID as JSON. Inspection and validation currently accept collection IDs, not arbitrary source paths. Validation exits unsuccessfully when checked records fail; inspect the `partial` flag before treating a bounded scan as complete. Query previews retain existing result caps. CLI exports are synchronous and atomically publish the completed destination; they do not create execution-history jobs. Use the browser/API for persisted background runs. For unattended CLI processing, use a separate workspace from a running server; cross-process generation coordination is not implemented.

## Remaining platform work

The broader platform roadmap is not complete. Remaining items include typed Parquet exports; general ZIP/gzip and encoding controls; array expansion and pivot/unpivot; fully visual cleanup controls; primary DuckDB pipeline execution; validation quarantine/skip policies; cron and remote imports; dataset versions/diffs/restoration; custom API paths and endpoint-specific keys/ACLs; signed outgoing webhooks; and large analytical engine comparisons. Existing per-collection APIs, bearer-key protection, optional CRUD, query publishing and OpenAPI remain available.

## Verification

Run `go test ./...` and `go vet ./...` with a compatible native compiler. Opt-in large-input measurements are documented in [the Windows performance report](performance-windows-2026-10-11.md), including the unsuccessful 1 GiB low-disk run, and [the Linux/Docker report](performance-linux-2026-10-11.md).

With Playwright installed, run `node scripts/browser-checks.cjs http://127.0.0.1:PORT/collections` against an isolated local test server. The script imports and deletes synthetic data and checks batch failures, pagination, quality rules, cleanup previews, undo/redo, recipe saving, exports, exclusions/restoration, themes and mobile overflow. Set `FLUXPORT_BROWSER_CHANNEL=msedge` to use installed Edge, or install Playwright Chromium. Node/Playwright are development-only test dependencies; serving FluxPort still needs neither.
